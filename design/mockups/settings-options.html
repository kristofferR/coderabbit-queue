Per-repo settings

4 UX options · same styling, different structure All pages ↩

The job: pick a repository, see what it inherits from the fleet, change what should differ, and understand the consequence before saving. The four options differ in how you get to a repo and how much you see at once — everything else (controls, wording, provenance, impact preview) is held constant.

A

Rail + long form

A list of repos on the left, and the selected repo's settings as one long scrolling page. What we have today.

fleet visible no hidden statelong scroll
Good Nothing is hidden behind a tab — you can read a repo's whole configuration in one pass, and the rail keeps the rest of the fleet in view for comparison.
Costly The page gets long as settings grow; the advanced half is far from the basics, and the rail eats horizontal room the forms could use.

B

Repo switcher + tabs

The repo is a dropdown in a header bar; settings are split across tabs, so each screen is short and single-purpose.

short screens full width for formsstate hidden in tabs

Costly You can't see a repo's whole configuration at once, and an unsaved change on another tab is easy to forget — needs a per-tab dirty marker.

C

Fleet table, expand a row to edit

No rail and no separate page: every repo is a row with its key settings as columns. Clicking a row expands it in place for editing.

compare across repos spot the odd one outcramped editing
Good Answers questions the other options can't: which repos have Bugbot off? which still inherit everything? Drift across the fleet is visible at a glance.
Costly Only a few settings fit as columns, so the deep ones live inside the expander; with many repos the table itself becomes the scroll problem.

Bulk matrix with multi-select

Notes on these options
  • Identical styling by design — judge structure, ordering and how much is visible at once.
  • Every option keeps the same three guarantees: Runs vs Required stay separate, provenance (fleet default vs override) is visible, and a save states its consequence first.
  • They can be combined: C or D as the Repos landing page, with A or B as the single-repo view.
