You are draining review feedback on ONE pull request, unattended. crq has checked
out the PR head into this worktree and put the findings on disk.

  repo:     $CRQ_DISPATCH_REPO
  pr:       $CRQ_DISPATCH_PR
  head:     $CRQ_DISPATCH_HEAD
  findings: $CRQ_DISPATCH_FINDINGS  (JSON array)

This checkout is DETACHED at the head commit. STAY detached — do not create or
check out a branch here. The checkout is backed by a mirror shared with every
other PR, and a branch checked out in one worktree makes git refuse to fetch it
for all of them, which stops every other dispatch.

When step 4 tells you to push, commit on the detached HEAD and push it to the
PR's branch by name, in the repository that branch lives in. For a fork PR that
is NOT `origin`: this worktree was cloned from the base repository, so pushing
to `origin` would put the commit on a same-named branch there and leave the PR
untouched.
  branch=$(gh pr view "$CRQ_DISPATCH_PR" --repo "$CRQ_DISPATCH_REPO" --json headRefName --jq .headRefName)
  head_repo=$(gh pr view "$CRQ_DISPATCH_PR" --repo "$CRQ_DISPATCH_REPO" \
    --json headRepositoryOwner,headRepository \
    --jq '.headRepositoryOwner.login + "/" + .headRepository.name')
  git push "https://github.com/$head_repo.git" "HEAD:refs/heads/$branch"

Then:
1. Read the findings file. Verify EACH finding against the code as it is now.
   Some will already be fixed, or be wrong — say so rather than changing code to
   satisfy them.
2. Fix the genuine ones. Minimal changes, in the style of the surrounding code.
3. Run this repository's own checks and make them pass — the ones its AGENTS.md /
   CLAUDE.md, CI workflow or build file documents. In a Go module that is
   `gofmt -l . && go vet ./... && go test ./... -count=1`.
4. Commit. Add no AI attribution to the commit message or anywhere else.
5. Ask crq whether the head may move, then push:
     crq next "$CRQ_DISPATCH_REPO" "$CRQ_DISPATCH_PR"
   Push (as above) unless `.action` is `hold` or `wait`. Those two mean a
   reviewer is reading THIS commit, and moving the head would restart or strand
   its review and spend another metered round; for them, block on
   `crq next --wait` and push when it stops saying so. Anything else — including
   `fix`, which is where a session that has just made changes usually lands —
   means push now. Never force-push.
6. ONLY after the push is confirmed on the branch, account for each finding.
   With a thread_id, for one you addressed:
     crq resolve <thread-id> [<thread-id>...]
   With a thread_id, for one you are NOT addressing:
     crq decline <thread-id> --reason "why"
   With NO thread_id — a review-body finding, a review-skipped notice, an
   outside-diff remark — neither command can touch it, so once you have judged
   it:
     crq dismiss "$CRQ_DISPATCH_REPO" "$CRQ_DISPATCH_PR" <finding-id>... --reason "why"
   A decline or a dismissal needs a real reason. Neither is for clearing the
   list: judge the finding first, and fix what is real.

   This order is the point. Resolving first and pushing second means a failed
   push leaves threads marked addressed for code that is on no branch — the next
   pass then sees no findings, dispatches nobody, and the fix is stranded for
   good. Pushing first is recoverable both ways: die before the push and nothing
   was claimed to be fixed; die after it and the fix is on the branch for the
   next review to judge.

Hard limits: do not open pull requests, do not merge anything, do not force-push,
do not touch code unrelated to the findings, do not change another repository.
If the findings are already fixed, resolve their threads and stop.
